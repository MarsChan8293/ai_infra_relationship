## Planner feedback

### 1. History must enter planning, not only execution

Run 2 immediately re-selected the same four unresolved maintainer actions from Run 1. The executor can suppress exact retries using the run log, but the planner should eventually consume action history directly and apply a cooldown / negative-yield penalty.

A minimal rule would be:

`same action_key + same source + unresolved within N days -> temporary priority penalty`

while still allowing retry after new evidence appears or after a cooldown period.

### 2. Partial outcomes need first-class representation

`weijinqian0 -> affiliation` did not resolve employer/school, but the action produced high-value identity evidence: official name `Jinqian Wei` plus committer status. A binary success/failure label loses this information.

Future history should record at least `success / partial / unresolved / rejected`, plus concrete deltas such as `identity_resolved`, `role_verified`, `new_node`, `new_edge`, and `evidence_upgraded`.

### 3. Search actions can open a different high-value edge

`管文宇 -> affiliation` succeeded because merge metadata included both a corporate email domain and explicit collaboration context. This is a useful example of an action being answered by repository metadata rather than a personal biography page.
